## 2. 設計判断とトレードオフ

- **2026-11-25 経路は直線距離 × 迂回係数で概算する**：経路エンジン（OSRM など）は精度が高いが、インフラとコストが重い。MVP では誤差を許容し、係数を定数にして後で調整できるようにした。
- **2026-11-25 ポートの組み合わせは K×K の全探索**：最寄りの 1 組だけだと「少し歩けば空きのあるポート」を見落とす。K=10 なら 100 通りで計算量は小さい。→ **PHASE 3 で、最適解を保証する分枝限定法に変更した**（下記）。
- **2026-11-25 データ取得失敗時は 503**：ダミー値を返すと、利用者が実在しない空き台数を信じてしまう。可用性より正しさを優先した。
- **2026-11-25 品質ゲートを `scripts/check.py` の 1 か所に集約**：人・Hook・CI が同じ入口を使うので、「ローカルでは通るのに CI で落ちる」というずれを減らせる。標準ライブラリのみで書き、どの Python でも起動できる。
- **2026-11-25 コミットには GitHub の noreply メールアドレスを使う**：公開リポジトリのコミット履歴に個人のメールアドレスが残らないようにする。グローバル設定は変えず、このリポジトリのローカル設定（`git config user.email`）にだけ設定する。
- **2026-11-25 初回コミットの前に reviewer による最終レビューを行う**：ハーネスそのもの（権限設定・Hook）が後続のすべての作業の前提になるため、独立した視点で確認してから履歴に残す。
- **2026-11-25 依存は Lambda 成果物と同じ版に固定**：`requirements.txt` はランタイム用、`requirements-dev.txt` は開発用に分け、zip に開発ツールが入らないようにした。
- **2026-11-25 CI は `scripts/check.py` を呼ぶだけにする**：ワークフローに書くのは環境構築（checkout、Python 3.12、依存の導入）だけで、チェックの中身は check.py に置く。CI では venv を作らず `CHECK_PYTHON=python` で setup-python の 3.12 を使う。`permissions: contents: read`、`persist-credentials: false`、`timeout-minutes` で権限と実行時間を最小限にした。
- **2026-11-25 Actions はメジャータグ（`@v5`）で指定**：タグは付け替えられるので、コミット SHA に固定するほうがサプライチェーン攻撃に強い。今回は MVP の完成を優先してタグ指定とし、SHA 固定は今後の改善事項とした（progress.md の「今後の改善事項」）。
- **2026-11-25 `main` のブランチ保護は「PR 必須 + CI 必須 + force push とブランチ削除の禁止」で、レビュー承認は不要**：個人開発ではレビュー承認を必須にすると自分でマージできなくなる。人のレビューの代わりに、reviewer サブエージェントと CI で品質を担保する。必須のステータスチェックはジョブ名 `check` で参照するので、ジョブ名を変えると保護が効かなくなる点に注意。
- **2026-11-25 ブランチ保護は classic の branch protection ではなく ruleset を使う**：ruleset は JSON で宣言的に定義でき、`GET /rules/branches/{branch}` で適用結果を確認できる。bypass を空にして管理者も例外にしないことで、「CI を通さずに main を変える」経路をなくした。必須チェックは `integration_id`（GitHub Actions = 15368）まで指定し、他のアプリが同じ名前のチェックを出して成りすますのを防ぐ。
- **2026-11-25 ブランチ保護の検証は API と通常の PR で行う**：`git push --dry-run` はサーバー側のルールを評価しないので、根拠にならない。検証のために main へ実際に push すると、保護が効いていなかった場合に履歴が汚れる。そのため、API で適用内容を確認し、通常の PR でマージがブロックされる状態（CI が完了する前）からマージできる状態（CI が成功した後）に変わることを観察した。直接 push が拒否されるかどうかは未検証として扱う。
- **2026-11-25 GitHub の操作範囲を許可リストで CLAUDE.md に書く**：同じ認証情報で複数の Organization にアクセスできるため、エージェントの誤操作の影響範囲を 1 リポジトリに限定した。公開ファイルに Organization の実名を残さないよう、「禁止リスト」ではなく「許可リスト」の形式にした。その後、技術調査のための外部の公開リポジトリや公式ドキュメントの読み取りは許可された（変更操作と非公開リポジトリへのアクセスは禁止のまま）。

- **2026-11-25 大阪エリアの判定は「名前の形式 + 範囲 + 除外リスト」**（PHASE 3）：GBFS に地域の項目がない（`system_regions` は 404、`region_id` は全国にまたがる）。実データでは大阪市付近のポート 750 件中 747 件の名前が `A-96.` のように「英字 1 文字-番号.」で始まる（区ごとのエリアコードと推測）。同じ形式は那覇・長野にもあるので範囲で絞り、東大阪市内と判断した 2 件（Z-02、Z-03）を除外した。公式には「大阪エリア以外では返却できない」とあるため（docomo-cycle.jp/osaka）、**市外のポートに返却させる誤り（重大）よりも、市内のポートを取りこぼす誤り（経路が少し遠回りになるだけ）を許容する**安全側の判断にした。行政区域のポリゴンによる厳密な判定は、データの追加と依存が増えるので見送った。
- **2026-11-25 組み合わせの評価は、K×K の近似から「最適解を保証する分枝限定法」に変更した**（PHASE 3、ユーザーの指示による最終確認で変更）：
  - 3 つの方式を、実データ（745 ポート、プリセット 56 組）で計測した。

    | 方式 | 1 回の計算時間（中央値 / 最大） | 評価した組の数 | 最適解の保証 |
    |---|---|---|---|
    | 近い順に K=10 件ずつ（当初の実装） | 1.9ms / 2.1ms | 100 | **なし**（56 組では偶然一致した。11 番目以降のほうが速い反例を手計算で作れる） |
    | 全組の素朴な総当たり | 677〜778ms / 691〜824ms | 約 33〜34 万 | あり |
    | **分枝限定法（採用）** | **3.1ms / 4.5ms** | 中央値 約 180、最大 約 1,000 | **あり**（総当たりと全組で一致） |

  - 素朴な総当たりはローカルで約 0.7〜0.8 秒かかる。Lambda のメモリ 256MB では CPU の割り当てが 1 vCPU 未満なので、数倍遅くなると見込まれる（**未計測の推定**）。MVP の応答時間としては厳しい。
  - **分枝限定法**：貸出ポート A ごとに「A を使う組の合計所要時間の下限」を計算し、下限の小さい順に調べる。下限が暫定の最良値を超えたら、残りの A は最適解になりえないので打ち切る。
    - 下限 = 徒歩(出発地→A) + 手続き 2 分 + 「A→目的地の直線距離」を速いほう（自転車）の速度で進む時間
    - 根拠 1：返却ポートから目的地までの徒歩は、同じ距離を自転車で進むより遅い。
    - 根拠 2：A→B→目的地の距離は、A→目的地の直線距離以上になる（**三角不等式**。大円距離は距離の公理を満たす）。
    - A を固定したときも、合計 ≥ 徒歩(出発地→A) + 手続き + 徒歩(B→目的地) なので、B を目的地に近い順に調べて同様に打ち切る。
    - 打ち切りは数学的に正しい下限だけを使うので、結果は全探索と同じになる（近似ではない）。浮動小数点の丸め誤差で誤って打ち切らないよう、比較に 1e-9 分の余裕を持たせた。合計が同じ組も、ID による同値の扱いまで含めて全探索と一致する。
  - 最悪の計算量は O(貸出可能数 × 返却可能数) のまま。下限がほとんど効かない配置では、総当たりと同程度（約 0.8 秒）まで遅くなりうる。実データでは、評価する組が全組の 0.3% 以下だった。
  - 検証：
    - ランダムな配置 200 通りで、テスト側に独立して書いた素朴な全探索と、結果（合計と採用ポート）が一致することを確認するテストを追加した。
    - 実データでは `smoke_gbfs.py` が素朴な総当たりと照合する。
    - さらに、下限をわざと誤った値（徒歩の速さで計算した、大きすぎる値）に変えて実行し、138 件のテストが失敗することを確かめた（**ミューテーションテスト**の考え方：テストがバグを検出できるかを、バグを入れて確かめる）。
  - 当初の K=10 方式を採用した理由は「計算量が小さい」だった。しかし、最適解を保証しないことが、API の利用者から見えない欠点だった。分枝限定法は同程度の速度で保証も得られるので、K というパラメータ自体を削除した（設定項目も減る）。
- **2026-11-25 失敗時の扱いを階層ごとに分けた**（PHASE 3）：フィード全体の構造が壊れている、データが古すぎる（900 秒超）、大阪エリアのポートが 0 件のときは、全体を失敗にして 503 を返す。個々のポートのレコードが壊れているときは、そのポートだけを捨てて残りで計算する。1 件の不正で全体を止めないが、「怪しい値で計算する」ことはしない。真偽値が欠けているレコードも、偽とみなさずに捨てる。
- **2026-11-25 キャッシュは ttl の間だけで、期限切れのデータは失敗時にも返さない**（PHASE 3）：ttl はフィードの値（60 秒）を使い、300 秒を上限とした。取得に失敗したら、古いキャッシュで取り繕わず 503 を返す。Lambda では実行環境が再利用される間だけキャッシュが効く。複数スレッドからの同時取得を防ぐために `threading.Lock` を使った（uvicorn では同期エンドポイントがスレッドプールで動くため）。
- **2026-11-25 入力の検証を GBFS の取得より先に行う**（PHASE 3）：422（形式）→ 400（地点が存在しない・同じ地点）→ 503 の順に判定する。入力が誤っているリクエストで外部 API にアクセスしない。
- **2026-11-25 おすすめの判定は丸める前の値で比較し、同じ値なら徒歩**（PHASE 3）：API の応答では 0.1 分単位に丸めるため、画面上では同じ値に見えても自転車がおすすめになることがありうる。誤差の範囲なので許容した。
- **2026-11-25 キャッシュが効いている間も、データの古さを確認する**（PHASE 3、reviewer の指摘）：ttl を最大 300 秒まで受け入れるので、取得時点で 890 秒前のデータを、さらに最大 300 秒返し続けることがありうる。キャッシュを使う前にも 900 秒の閾値を確認する。あわせて、現在より 300 秒以上未来の `last_updated` も不正なデータとして扱う（極端な値で `datetime` の変換が 500 になるのも防ぐ）。
- **2026-11-25 データの時刻は、2 つのフィードの `last_updated` のうち古いほう**（PHASE 3）：結合したデータの鮮度は、古いほうのフィードで決まるため。応答では JST の ISO 8601 形式（`+09:00`）で返す。

- **2026-11-25 フロントエンドは「UI（App.tsx）・API クライアント（api/client.ts）・型（api/types.ts）・地図（RouteMap.tsx と純粋関数の mapPoints.ts）」に分けた**（PHASE 4）：画面の状態は `useState` の判別共用体（`idle` / `loading` / `success` / `error`）で表し、状態管理ライブラリは入れない。コンポーネントは App.tsx 内の小さな関数に留め、ファイルを分けたのは Leaflet に依存する地図だけ（テストで差し替えるため）。
- **2026-11-25 API の型は OpenAPI スキーマを出力して手で書いた**（PHASE 4）：コード生成ツール（openapi-typescript など）は依存とビルド手順が増えるので、モデルが 8 個の MVP では見送った。`DataSource` の既定値つきのフィールドは OpenAPI では required ではないが、サーバーは常にシリアライズするので必須の型にした。実行時には、UI が依存する骨格だけを型ガードで確かめ、想定外の本文はエラーとして扱う（それらしい結果を出さない）。
- **2026-11-25 エラーは API クライアントで種類（`input` / `gbfs_unavailable` / `network` / `server` / `invalid_response`）に変換する**（PHASE 4）：UI は HTTP のステータスコードを知らなくてよい。400 はサーバーの `detail`（日本語）をそのまま表示し、422 の `detail`（配列）は表示しない。失敗したら前回の結果も消す（古い結果を今の結果に見せない）。連続して検索したときは、最後のリクエストの応答だけを反映する。
- **2026-11-25 未選択と同じ地点は、API を呼ぶ前に画面で入力エラーにする**（PHASE 4）：サーバーも 400 を返すが、GBFS の取得を伴うリクエストを無駄に送らないため。
- **2026-11-25 API は同一オリジンの相対パス（`/api/...`）で呼ぶ**（PHASE 4）：本番は CloudFront で `/api/*` を API Gateway に振り分ける想定で、CORS が不要になる。ローカルは Vite の `server.proxy` で `127.0.0.1:8000` に転送する。別オリジンにする場合だけ `VITE_API_BASE_URL` を設定する。
- **2026-11-25 地図の線は破線の直線にし、凡例と注意書きで「概算」を明記した**（PHASE 4）：所要時間は直線距離 × 迂回係数なので、実線で道路のように見せると誤解を招く。大阪エリア判定の仮定があるため、利用前に公式アプリで確認するよう画面に書いた。
- **2026-11-25 Node.js を 22.11.0 から 22.23.5 に更新した**（PHASE 4）：
  - **理由**：最新版のライブラリが、22.11.0 では動かなかった。Vite 8・Vitest 5・ESLint 10 は Node 22.12 以上、jsdom 31 は 22.22.2 以上が必要。
  - **検討した案**：(1) Node 22 系の最新に更新する、(2) Node は据え置いて、古い系統（Vite 6.4 / Vitest 3.2 / ESLint 9.39 / jsdom 26）に固定する、(3) Node 24 以降に上げる。
  - **承認**：ユーザーに確認し、(1) の「メジャーは変えずに最新のライブラリを使う」が選ばれた。実行者も確認し、「Claude が winget で実行」が選ばれた。`winget upgrade --id OpenJS.NodeJS.22 --exact` を実行し、インストーラーの管理者権限の確認（UAC）はユーザーが承認した。
  - **反映**：`package.json` の `engines`（`>=22.22.2 <23`）と `.nvmrc`（`22`。CI の setup-node が読む）で 22 系を指定した。CI でも Node 22.23.5 で動くことを確認した（PR #4）。
- **2026-11-25 品質ゲートに frontend の `build` を加えた**（PHASE 4）：型チェックとテストが通ってもビルドで落ちる問題（Vite の設定、アセットの解決）を、CI で検出するため。依存のインストール（`npm ci`）は環境構築として CI のワークフロー側に書き、check.py は `node_modules` がなければ環境不備（exit 2）にする。

## 3. AI 駆動開発で得られた知見

- **2026-11-25** 調査段階では「確認済みの事実」と「推測」を分けて報告させた。デプロイ状況のように、ローカルからは確認できない事項を早く洗い出せた。
- **2026-11-25** 自分で追加した deny ルール `Bash(rm -rf *)` が、Claude 自身の venv 再作成コマンドをブロックした。権限ルールは Claude の自己判断より優先されることを実地で確認できた。代わりに非破壊の手段（パッケージの入れ替え）を取った。
- **2026-11-25** サブエージェントの価値は「並列化」よりも「コンテキストの隔離と独立した視点」にある。Pro の利用枠では、委譲するたびにコンテキストを一から作り直すコストがかかる。そのため、単純な作業はメインで行い、大量の読み込みが必要な作業や独立した評価が必要な場面に限って委譲する。
- **2026-11-25** reviewer に初回コミット前の全ファイルを見せたところ、「PowerShell 経由では `git commit` の ask が効かない」という穴が見つかった。権限ルールはツール（Bash / PowerShell）ごとに照合されるため、両方に書く必要がある。自分で書いたルールの抜けは、独立した視点のほうが見つけやすい。
- **2026-11-25** ユーザーが伝えたアカウント名（表示名）と、`gh api user --jq .login` の実際の login が違っていた。リポジトリのパスは login で決まる。外部に影響する操作の前に、識別子を API で確認してから実行することで、誤った名前空間への作成を防げた。
- **2026-11-25**（PHASE 3）researcher に、大阪エリアの範囲・ポート名の接頭辞・バッテリー交換専用の拠点・ODPT の規約を調べさせた。公式に確認できたのは「大阪エリアは大阪市で、エリア外には返却できない」ことだけで、残りは「公式資料なし」という結果だった。判定方法は、実データの分析（メインで実行）から決めた。**一次情報で裏付けられない仕様は、実データから仮定を立て、仮定であることを記録する**という分担がうまく機能した。

## 4. ハーネス各設定の目的

| 設定 | 目的 |
|---|---|
| `CLAUDE.md` | 毎セッション読み込まれる。変えてはいけない要件・アーキテクチャ・開発フロー・完了条件だけを書く（規約は rules に分離） |
| `.claude/rules/*.md`（`paths` 付き） | 該当ファイルを触ったときだけ読み込まれる規約。コンテキストを節約し、CLAUDE.md との重複を避ける |
| `.claude/settings.json` の permissions | allow：品質チェックと git add のみ。ask：commit/push・AWS・依存追加・削除。deny：機密ファイルの Read、`rm -rf`、force push、`reset --hard` |
| Stop Hook（`scripts/stop_hook.py`） | 応答終了時に品質ゲートを自動で検証し、「テストを通さずに完了報告する」ことを防ぐ |

### Stop Hook の挙動
| 状況 | 挙動 |
|---|---|
| 監視対象（backend/frontend/scripts）に前回チェック以降の変更なし | 何もしない（約 0.1 秒） |
| 変更あり・チェック成功 | 何もしない（状態を保存） |
| 変更あり・失敗・初回 | `decision: block` で失敗ログを Claude に返し、修正させる |
| 差し戻し後（`stop_hook_active: true`）も失敗 | **block しない**。`systemMessage` でユーザーに通知して終了（無限ループ防止） |
| 環境不備（venv なし）・タイムアウト | block しない。`systemMessage` で通知 |

- 二重の安全策として、Claude Code 本体にも「Stop Hook による継続は連続 8 回まで」という上限がある。
- Windows 対応：exec 形式（`command: "python"`, `args: [...]`）で起動し、シェルのクォート問題を避けた。stdout の JSON は `ensure_ascii=True` で出力し、コンソールの文字コード（cp932）に依存しないようにした。
- 制約：Bash の権限ルールはコマンド文字列とのマッチングでしかない。たとえば `Read` の deny は `cat .env` を防げない。厳密に守るにはサンドボックスが必要。

### サブエージェント（2026-11-25 導入、Claude Code 2.1.305）

**目的**
1. コンテキスト管理：大量のドキュメントや差分の読み込みを別のコンテキストに隔離し、メインには要約だけを戻す
2. 専門性の分離：役割ごとのシステムプロンプトと観点のチェックリスト
3. 独立した評価：実装者（メイン）とは別のコンテキストで評価させ、確証バイアスを減らす

| エージェント | tools | 外した権限とその理由 |
|---|---|---|
| researcher | Read, Grep, Glob, WebFetch, WebSearch | Bash/Edit/Write なし：調査に変更系の操作は不要 |
| reviewer | Read, Grep, Glob | Web なし：レビューはリポジトリ内で完結する。Bash なし：diff はメインが渡す |
| evaluator | Read, Grep, Glob | 同上。さらに、実装コードを読まないよう指示している |
| aws-expert | Read, Grep, Glob, WebFetch, WebSearch | Bash なし：AWS CLI を実行させない。読み取り系のコマンドもメインがユーザーの了承を得て実行し、結果を渡す |

**設計判断**
- **全員から Bash を外した**：公式ドキュメントにも「Bash があれば Edit/Write がなくてもファイルを変更できる」とある。`git diff` のような読み取りは、メインが実行して結果を渡せば足りる。
  - トレードオフ：レビュー対象の取得をメインに頼るので、渡し漏れが起きうる。渡す内容（ファイル一覧と diff）を手順として固定して補う。
- **`Agent` も tools に含めない**：既定ではサブエージェントがさらにサブエージェントを 3 階層まで起動できる。利用枠が膨らむのを防ぐ。
- **`model: sonnet`**：Claude Pro の利用枠を考慮した。重要な設計レビューだけは、呼び出し時の `model` 指定で上位モデルに切り替える。
- **`maxTurns` で上限を設定**：調査が際限なく続くのを防ぐ（15〜25 ターン）。
- **evaluator の独立性は指示で担保**：プロンプトで「実装コードを読まない」と制約し、メインからは要求仕様だけを渡す。
  - PreToolUse Hook で読み取りを機械的にブロックする方法もあるが、MVP では仕組みが過剰と判断して見送った。逸脱が見られたら導入する。
- **見送ったもの**：`memory`（永続化は `docs/progress.md` で行う）、`isolation: worktree`（変更しないので不要）、Agent Teams（大規模すぎる）。

**運用（具体的な流れ）**
```
新機能 X：
  1. (必要なら) researcher：X に関わる外部仕様を調査 → メインが docs/plan.md に反映
  2. evaluator：docs/plan.md の X の要求仕様だけを渡す → テストケース表
  3. メイン：表をもとにテストを書く → 実装 → scripts/check.py
  4. reviewer：変更ファイルの一覧と diff を渡す → 指摘 → メインが修正
  5. メイン：progress.md を更新 → ユーザーにコミットの承認を求める
```
- 同時に起動するのは原則 1 つまで。並列にするのは、互いに独立した調査が 2 つ以上あるときだけ。
- サブエージェントの出力は「提案」として扱う。採否はメインが判断し、採用した内容をリポジトリに記録する。

### セッション管理
- **`docs/progress.md`**：状態（フェーズ、タスク、ブランチ、未解決の問題、品質チェック結果、次にやること）を 1 ファイルにまとめる。CLAUDE.md から `@import` しているので、毎回のセッション開始時に自動で読み込まれる。
- **ファイルの役割分担**：plan.md は「何を作るか」、engineering-notes.md は「なぜそうしたか・何を学んだか」、progress.md は「いまどこにいるか」。重複を避け、どこに何を書くかを迷わないようにする。
- **トレードオフ**：progress.md は手動で更新するので古くなりうる。フェーズ完了時とセッション切り替え前に更新することを CLAUDE.md のルールにし、Git の状態（`git status` / `git log`）とあわせて確認させることで補う。

## 6. 技術面接で説明できる重要事項

- API Gateway HTTP API と Lambda のプロキシ統合で、Mangum が何を変換しているか（payload 2.0 から ASGI scope へ、レスポンスから `statusCode` / `body` へ）。
- Lambda にネイティブ拡張を含む依存を載せるときの落とし穴（OS・CPU アーキテクチャ・Python の ABI が一致している必要がある）。
- 「最寄りポート」と「組み合わせの評価」で結果が変わる例と、計算量の見積もり。全探索（O(N²)）を、下限による打ち切り（分枝限定法）で、最適解を保証したまま約 200 倍速くした理由と、その正しさの根拠（三角不等式）。
- データ取得に失敗したとき、フォールバックで値を返すのではなくエラーを返す判断の理由。
- CI・Stop Hook・手動実行で同じ品質ゲートを共有する設計と、ブランチ保護で「CI が通らないとマージできない」ことを仕組みにした理由。
- AI エージェントの品質を「指示（CLAUDE.md）」ではなく「仕組み（Hook と権限）」で担保する設計と、無限ループを防ぐ方法。
- 実データで「最寄りのポート同士が最短とは限らない」例（PHASE 3）。梅田→難波では、難波に最も近い返却ポート（E-42、約 250m）ではなく、梅田側にある B-16（約 410m）を選ぶ。自転車の区間が短くなる効果が、徒歩の増加を上回るため。近くの B-58 は空きドックが 0 なので、候補に入らない。
- テストで実装の写しにならない期待値の作り方（PHASE 3）。全ポートを同じ経線上に置くと、ハバーサイン式の距離は「地球の半径 × 緯度差」になり、手で計算できる。実データのフィクスチャでは、テスト側に独立した総当たりの計算（オラクル）を書いて、結果を照合する。

## 7. 経路検索バックエンドの仕組み（PHASE 3、2026-11-25）

### モジュールの構成
| ファイル | 役割 | 依存 |
|---|---|---|
| `backend/app/routing.py` | ハバーサイン式、利用可否の判定、組み合わせの評価（分枝限定法）。**純粋関数**（入力：地点とポート一覧、出力：結果） | なし |
| `backend/app/gbfs.py` | 取得（urllib、タイムアウト 4 秒）、構造の検証、結合、大阪エリアの判定、ttl キャッシュ | routing（`Station` 型だけ） |
| `backend/app/presets.py` | プリセット地点（8 か所）。ここ 1 か所だけで定義する | なし |
| `backend/main.py` | FastAPI のエンドポイントと Pydantic モデル、`handler = Mangum(app)` | 上記すべて |
| `backend/tools/smoke_gbfs.py` | 実 GBFS への疎通確認と性能計測（手動実行。pytest の対象外） | 上記 |

- C# でいえば、`routing.py` はドメイン層の static メソッド群、`gbfs.py` はリポジトリ（データアクセス）層、`main.py` はコントローラ層に相当する。
- **依存性の注入（DI）**：FastAPI の `Depends(get_gbfs_client)` で GBFS クライアントを受け取る。テストでは `app.dependency_overrides` で偽のクライアント（フィクスチャを返す取得関数と、固定の時計）に差し替える。本番コードにテスト専用の分岐を入れずに、ネットワークを使わずにテストできる。
- `GbfsClient` は、取得関数（`fetch`）と時計（`clock`）をコンストラクタで受け取る。キャッシュの ttl の境界は、時計を進めるだけで決定的にテストできる。
- `@dataclass(frozen=True)` は、C# の `record`（不変の値オブジェクト）に近い。Pydantic モデルは API の入出力だけに使い、内部のデータには軽量な dataclass を使う。

### API
- `GET /api/presets` → `{presets: [{id, name, lat, lon}]}`。GBFS には接続しない。
- `POST /api/routes/search`（`{origin_id, destination_id}`）→ `origin`、`destination`、`recommended`（`bike_share` / `walk`）、`bike_share`（貸出・返却ポート、各区間の距離と分、合計。候補がなければ `null`）、`walk`、`data`（`last_updated`、提供者、ライセンス、クレジット表記）。
- エラー：422（形式）、400（`指定された地点が見つかりません` / `出発地と目的地が同じです`）、503（`ポート情報を取得できませんでした。…`）。GbfsError 以外の想定外の例外は 500 になり、経路は返さない。

### 計算式（`RouteParams` の既定値）
```
距離 = ハバーサイン式の直線距離（地球の半径 6,371,000m）× 迂回係数 1.3
合計 = 徒歩(出発地→A)/4.8km/h + 貸出 1 分 + 自転車(A→B)/15km/h + 返却 1 分 + 徒歩(B→目的地)/4.8km/h
A：貸出可能（is_installed ∧ is_renting ∧ 空き自転車 > 0）な全てのポート
B：返却可能（is_installed ∧ is_returning ∧ 空きドック > 0）な全てのポート
A = B の組は除外し、全ての (A, B) の中で合計が最小の組を採用する（同じ値なら station_id の辞書順）
→ この所要時間モデルでの最適解を保証する。計算は分枝限定法で打ち切るが、結果は全探索と同じ
```
- 手続きの 2 分があるので、約 180m 未満の移動では徒歩のほうが速い（テスト B10）。

### 技術的負債：大阪エリアの判定（2026-11-25 記録）
**現状の仮定**（`backend/app/gbfs.py` の `is_osaka_station`）
- 名前が `^[A-Z]-\d+\.`（例：`A-96.`）で始まる ∧ 緯度 34.55〜34.78・経度 135.35〜135.65 ∧ 除外リスト（東大阪市内の 2 件：ID 7808、7810）に含まれない。
- 根拠：実データでは、範囲内の 750 件中 747 件がこの名前の形式で、残りの 3 件はバッテリー交換専用の拠点だった。公式資料で確認できたのは「大阪エリアは大阪市で、エリア外には返却できない」ことだけである。名前の接頭辞の意味は、公式資料で確認できていない。

**誤判定の可能性**

| 種類 | 起こりうる例 | 影響 |
|---|---|---|
| 市外のポートを含めてしまう | 東大阪市・吹田市・豊中市・尼崎市などに、同じ名前の形式のポートが追加される（範囲は矩形なので、境界付近の隣接市を含む）。既存の 2 件は除外リストで手当てしているだけ | **重大**。返却できないポートに案内してしまう |
| 市内のポートを落としてしまう | 名前の形式が変わる（例：`AA-01.`、全角文字、接頭辞なし）、新しいポートを市外と誤って除外リストに入れる | 経路が少し遠回りになる（最適でなくなる） |
| 名前の形式の意味が変わる | 事業者が命名規則を変える | どちらも起こりうる |

- 現在の検出手段：実データでの手動の確認（`smoke_gbfs.py` のポート数）だけ。自動では検出できない。

**将来的な改善方法**（効果の大きい順）
1. **大阪市の行政区域のポリゴンで判定する**：国土数値情報（行政区域データ）などから大阪市の境界を取得し、点がポリゴンの内側にあるかで判定する（point-in-polygon）。矩形の範囲と除外リストを置き換えられる。境界データの同梱と、そのライセンスの確認が必要。判定自体は標準ライブラリだけで書ける（レイキャスティング法）。
2. **事業者に確認する**：エリアコード（接頭辞）の意味と、市外のポートの扱いを、ドコモ・バイクシェアのサポートに問い合わせる。
3. **変化を検知する**：`smoke_gbfs.py` か定期実行で、「範囲内で名前の形式に合わないポート」「範囲の境界付近の新しいポート」「大阪エリアのポート数の急な増減」を報告する。誤判定をすぐに見つけられる。
4. **公式のポート地図と突き合わせる**：docomo-cycle.jp の大阪エリアのポート一覧と、判定の結果を比べる。

### 9.4 1 秒 1 リクエストを守る設計（推論を含む）
- **確認済み**（AWS 公式）：
  - Lambda の予約済み同時実行数は追加料金なしで設定できる。超えた呼び出しは 429（`TooManyRequestsException`）になる。
  - HTTP API のスロットリングは token bucket 方式で、**best-effort**（上限は保証されない）。
- **推論**：同時実行数を 1 にしても、同時に動く数が 1 になるだけで、リクエストの間隔は保証されない。そこで、プロセス内のリミッター（前回の送信から 1.1 秒空ける）と組み合わせる。
- **残るリスク**：実行環境が入れ替わった直後は、前回の送信時刻が分からない。初回の送信の前にも待つことで緩和する。同時実行数が 1 なら、この待機で間隔が保証されると考えられる（§9.6 の推論）。
- **採用しなかった案**：DynamoDB などによる分散リミッター。MVP では過剰と判断した。

### 9.5 利用規約への対応（2026-11-25、開発者本人が確認し、採用を承認）

- FOSSGIS の利用規約：https://www.fossgis.de/arbeitsgruppen/osm-server/nutzungsbedingungen/
- FOSSGIS OSRM：https://routing.openstreetmap.de/about.html
- Nominatim：https://operations.osmfoundation.org/policies/nominatim/

**採用の前提**：個人利用・非商用・低頻度。この前提で、FOSSGIS OSRM と Nominatim の採用が承認された。

| 条件 | 対応方法（PHASE 4.5 で実装、plan §6.7〜6.9） |
|---|---|
| 各サービスへのリクエストは、アプリ全体で 1 秒に 1 回以下 | サービスごとに、プロセス全体で共有するリミッター。本番では Lambda の予約済み同時実行数を 1 にする（PHASE 6） |
| OSRM の徒歩と自転車は、共通のリミッターで制御する | `routed-foot` と `routed-bike` で、1 つのリミッターを共有する |

| 1.1 秒以上の間隔で、直列に送る | `time.monotonic` で前回の送信から 1.1 秒待つ。プロセスの起動後の最初の送信の前にも待つ |
| 自動リトライで過剰にアクセスしない | 自動リトライは実装しない。失敗したら 503 |
| アプリを識別できる User-Agent | `ChariRoute/0.1 (+https://github.com/EnKyria/chariroute-lab)`（設定で変更できる。個人のメールアドレスは入れない） |
| 技術的に可能なら、適切な Referer | `OUTBOUND_REFERER` が設定されているときだけ付ける（本番の URL が決まったら設定する） |
| ライセンスとクレジットの表記 | OSM（ODbL）、OSRM / FOSSGIS、Nominatim、GBFS（CC BY 4.0）を画面に表示する |
| OSM の地図修正リンク | https://www.openstreetmap.org/fixthemap へのリンクを表示する |
| 大量のアクセス、スクレイピング、負荷試験をしない | 実 API の確認は最小限のスモークテスト（Table 2 回・Route 3 回）だけ。自動テストはフィクスチャとスタブを使う |
| URL を設定で切り替えられる | `OSRM_FOOT_URL` / `OSRM_BIKE_URL` / `NOMINATIM_URL`（https のみ） |
| Nominatim：オートコンプリート・定期的な検索・網羅的な検索をしない | 検索ボタンを押したときだけ、1 回呼ぶ |
| Nominatim：同じ検索を減らす | プロセス内のキャッシュ（24 時間・200 件）。入れるのは公開施設の結果だけ |
| **サイト運営者の連絡先メールアドレスを、容易に確認できるようにする**（FOSSGIS の正式な規約） | **未解決**。個人のメインのメールアドレスは勝手に公開しない。対応方法（公開用のアドレスを用意する／運営者に問い合わせる）が決まるまで、FOSSGIS の実 API を使わない（plan §6.10） |

**利用上の注意**：
- 外部サービスには**稼働の保証（SLA）がない**。規約の変更や、利用の停止・遮断がありうる。そうなったら 503 を返し、ダミーの経路は出さない。
- URL を設定で切り替えられるので、自前で立てた OSRM などにも移行できる。
- 一般公開や商用の利用に変える場合は、規約の範囲を超えるので、自前で立てるか、別のサービスにする必要がある。

### 9.6 PHASE 4.5 の設計判断（2026-11-25、ユーザーの最終決定）
- **徒歩のみの経路・比較・おすすめを廃止した**：Google マップで確認できる機能と重なるため。シェアサイクル固有の課題（ポートの組み合わせ、空き台数・返却枠、乗り換えの徒歩）に集中して、既存のサービスとの違いを出す。
- **OSRM の障害時は 503（B 案）**：直線距離の概算への自動フォールバックは、「道路の経路」と誤解されるおそれがある。正しさを優先して、取得できなかったことを明示する。
- **所要時間 = 道路距離 ÷ 独自の速度**（第一案、実環境での確認待ち）：
  - FOSSGIS の自転車プロファイルの所要時間は、電動アシストのシェアサイクルの実態より遅い（実測で約 8.5 km/h 相当）。
  - 速度をアプリ側で決めると、直線距離モデルと前提がそろい、パラメータとして説明できる。
  - 候補の選択（Table）と画面の表示（Route）で、同じ式を使う。
- **候補は直線距離で各 10 件 + 直線距離モデルの最適な組**：
  - Table の大きさ（最大 24 点）とリクエスト数（1 回の検索で 5 回）を抑えつつ、橋や川による遠回りを道路距離で評価できる。
  - 最適解は候補の中でだけ保証される（全体の最適解は保証しない）。
- **地点検索は POST で受ける**：検索語を、自アプリの URL や API Gateway・CloudFront のアクセスログに残さないため。ただし、Nominatim 側は GET なので、Nominatim のログには残りうる。このことを画面に明示する。
- **1 秒 1 リクエストの保証の考え方**（推論）：
  - Lambda の予約済み同時実行数が 1 なら、呼び出しは時間的に重ならない。
  - プロセス内のリミッターで 1.1 秒の間隔を空け、新しい実行環境では最初の送信の前に 1.1 秒待つ。
  - こうすると、前の実行環境の最後の送信（前の呼び出しが終わる前）から、新しい送信までに 1.1 秒以上が空く。
  - ローカルでは、uvicorn の 1 プロセスに限る。
  - 本番でこの前提を確かめられない場合は、本番での実 API の利用を始めない。
