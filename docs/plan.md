## 2. 経路計算（直線距離モデル、PHASE 3。PHASE 4.5 以降は候補の絞り込みと比較評価に使う。道路モデルは §6）

```
合計所要時間 = 徒歩(出発地 → 貸出ポート A) + 自転車(A → 返却ポート B) + 徒歩(B → 目的地)
```
- 距離はハバーサイン式で求めた直線距離 × 迂回係数（初期値 1.3）。
- 速度の初期値は徒歩 4.8 km/h、自転車 15 km/h。貸出・返却の手続き時間として各 1 分を加える。
- 候補の選び方：
  - A は「貸出可能な」全てのポート、B は「返却可能な」全てのポート。A = B の組は除く。
  - 全ての (A, B) の中で合計が最小の組を採用する。**この所要時間モデルでの最適解を保証する**（2026-11-25 変更）。
  - 計算は分枝限定法（合計の下限で、最適解になりえない組を打ち切る）。結果は全探索と同じで、実データでは 1 回 約 3ms（素朴な総当たりは約 0.7 秒）。根拠と計測は `docs/engineering-notes.md` §2・§7。
  - 当初の「近い順に K=10 件ずつ」の方式は、最適解を保証しないため廃止した。
- 徒歩のみの所要時間も計算して並べて返す。自転車のほうが遅い場合もそのまま返し、UI で判断できるようにする。→ **PHASE 4.5 で廃止**（徒歩のみ・比較・おすすめは扱わない。§6.3）
- パラメータは定数にまとめ、テストで値を固定する（評価駆動：代表的な地点ペアの結果を比較できるようにする）。

## 3. API（PHASE 3 で実装済み。PHASE 4.5 で §6.11 のとおり変更する）
- `GET /health`
- `GET /api/presets`：プリセット地点の一覧（id, name, lat, lon）。8 か所。`backend/app/presets.py` だけで定義する。
- `POST /api/routes/search`：`{origin_id, destination_id}` を受け取り、`origin`、`destination`、`recommended`（`bike_share` / `walk`）、`bike_share`（ポート A/B、各区間の距離と所要時間、合計。候補がなければ `null`）、`walk`、`data`（`last_updated`（JST）、提供者、ライセンス、クレジット表記）を返す。
  - 旧 `{origin, destination}` 文字列 API からの仕様変更。特性テストは置き換えた。
  - 判定の順序は 422（形式）→ 400（不明な地点・同じ地点）→ 503（GBFS の取得失敗）。
  - 503 にする条件：通信エラー、タイムアウト、HTTP エラー、不正な JSON、必須構造の欠落、大阪エリアのポートが 0 件、データが 900 秒より古い、`last_updated` が 300 秒より未来。
  - キャッシュは経過時間が ttl（フィードの値、上限 300 秒）未満で、かつデータが古すぎない間だけ使う。期限切れのキャッシュは失敗時にも返さない。
  - 個々のポートのレコードが不正なら、そのポートだけを捨てる。
  - `bike_share` は、利用可能な全ての貸出・返却ポートの組の中で合計所要時間が最小の組（このモデルでの最適解）。所要時間は直線距離 × 迂回係数による概算で、実際の道路の経路ではない。
  - `data.attribution` はクレジット表記（「出典：株式会社ドコモ・バイクシェア / 公共交通オープンデータ協議会（CC BY 4.0）のポート情報を加工して作成」）。`data.dataset_url` はデータセットのページ。

## 6. PHASE 4.5：地点指定の拡張と道路に沿った経路（**確定**、2026-11-25）

ユーザー受入テスト（PHASE 4）の結果を受けて、ユーザーが最終決定した仕様。これまでの計画（ORS 案、OSRM の初版）と矛盾する場合は、この節を優先する。
**状態：実装済み（2026-11-25、セッション 5、ブランチ `feature/phase45-implementation`）。** 6.10 は解決した。実装で決めた点と実 API の確認結果は engineering-notes §9.7。

### 6.1 サービスの目的
- 大阪市内でドコモ・バイクシェアを使う前提で、効率的な**貸出ポートと返却ポートの組み合わせ**を探す。
- Google マップなどの既存のサービスとの差別化を重視し、シェアサイクル固有の課題に集中する。課題とは、空き台数と返却枠、ポートの選び方、乗り換えの徒歩のこと。

### 6.2 技術選定（確定）
| 役割 | 採用 |
|---|---|
| ポート情報 | ODPT の GBFS（既存） |
| 道路の経路 | FOSSGIS OSRM（`routed-foot` / `routed-bike`） |
| 地点検索 | Nominatim |
| 現在地 | ブラウザの Geolocation API |
| 地図 | Leaflet + OpenStreetMap |
| バックエンド / フロント | Python・FastAPI / React・TypeScript |
| 本番 | AWS（PHASE 6） |

- 新規の API キー、有料の契約、クレジットカードの登録が要らない構成を維持する。**openrouteservice は採用しない。**

### 6.3 機能
- **地点の指定**：
  - 指定の方法：現在地（GPS）、地点検索（駅名・公開施設名）、プリセット、地図のタップ
  - 出発地と目的地は、どちらも自由に設定でき、入れ替えられる。
  - GPS は、次の状態をそれぞれ画面に表示する：権限の拒否、タイムアウト、非対応、取得の失敗、HTTPS でない。
- **経路**：3 区間（徒歩：出発地 → 貸出、自転車：貸出 → 返却、徒歩：返却 → 目的地）。
  - 区間ごとに、道路に沿った経路（地図に実線で描く）、道路距離、推定所要時間を表示する。
  - 合計の推定所要時間も表示する。
  - 貸出・返却ポートの名称、利用可能な台数と返却できる枠の数、GBFS の取得時刻も表示する。
- **廃止する機能**（Google マップで確認できるため）：徒歩のみの経路の計算と表示、徒歩との所要時間の比較、おすすめの移動手段の判定、時間の短縮効果の表示。
  - API の `recommended` と `walk` を削除する。あわせて、TypeScript の型、UI（比較・おすすめの表示）、テスト、ドキュメントを整理する。
  - テストの削除・変更の理由は、コミットメッセージと PR に書く。
- **利用できる経路がない場合**：利用できるポートの組や、道路でつながる組がないときは、「利用できるシェアサイクルの経路が見つかりませんでした」と明示する。徒歩への自動の切り替えはしない。

### 6.4 経路探索のアルゴリズム
1. GBFS から、利用可能な貸出ポート（`is_renting` かつ空き自転車 > 0）と返却ポート（`is_returning` かつ空きドック > 0）を取り出す（既存の処理）。
2. **候補を絞り込む**（直線距離）：
   - 貸出候補：出発地から近い順に 10 件 + 直線距離モデル（分枝限定法）で最適な組の貸出ポート
   - 返却候補：目的地から近い順に 10 件 + 同じく返却ポート
   - それぞれ重複を除く。**最大の候補数は、貸出・返却とも 11 件**。
   - 同じポートが両方の候補に入ることはありうる。その場合でも、貸出と返却が同じポートの組は評価しない。
3. **Table を 2 回呼ぶ**（`annotations=distance`。所要時間は使わない。6.5）：
   - 徒歩（routed-foot）：
     - 地点は [出発地, 貸出候補 ≤11, 返却候補 ≤11, 目的地] の **最大 24 点**。
     - `sources = [出発地, 返却候補…]`、`destinations = [貸出候補…, 目的地]` とし、**最大 12×12 = 144 要素**を得る。
     - 使うのは、出発地 → 貸出候補（≤11）と、返却候補 → 目的地（≤11）の 22 要素。
     - 1 回で済ませるため、残りの要素は捨てる。
   - 自転車（routed-bike）：地点は [貸出候補 ≤11, 返却候補 ≤11] の **最大 22 点**。貸出候補 × 返却候補で **最大 11×11 = 121 要素**。
   - どちらも、OSRM の既定の上限（100 地点）より十分小さい。
4. **全ての組を評価する**：候補の全ての組（最大 121 組。貸出と返却が同じポートの組は除く）について、合計の推定所要時間を計算し、最小の組を選ぶ。
   - 合計 = 徒歩の距離 ÷ 4.8 km/h + 貸出の手続き 1 分 + 自転車の距離 ÷ 15 km/h + 返却の手続き 1 分 + 徒歩の距離 ÷ 4.8 km/h
   - 同じ値の組は、既存と同じ ID の順で決める。
5. **Route を 3 回呼ぶ**：選ばれた組の 3 区間について、`overview=full&geometries=geojson` で経路の形状と距離を取得する。
- **1 回の検索のリクエスト数**：Table 2 回 + Route 3 回 = **5 回**（GBFS を除く）。
- **null と通行できない組の扱い**：
  - Table の距離が `null`（到達できない）なら、その区間を含む組を除外する。
  - 貸出候補へ徒歩で到達できない、または目的地へ徒歩で到達できない場合は、そのポートを候補から除く。
  - 残った組が 0 件なら、「利用できるシェアサイクルの経路が見つかりませんでした」（`bike_share: null`、HTTP 200）にする。
  - OSRM の `code` が `NoTable` / `NoRoute` / `NoSegment` の場合も、経路なしとして扱う。それ以外のエラー（`InvalidQuery`、`TooBig`、HTTP 5xx、タイムアウト、不正な応答）は 503 にする。
- **地点のスナップ**：出発地か目的地が道路から大きく離れている場合（Table の `sources` / `destinations[].distance` が 300 m を超える）は、400「近くに道路が見つかりません」にする。値は実装で調整する。
- **最適性の制約（画面とドキュメントに明示する）**：
  - 結果は「直線距離で絞り込んだ候補（最大 11×11 組）の中で、推定所要時間が最小」の組である。**全てのポートの組の中での最適解は保証しない**。
  - 川や橋で遠回りが必要な場合は、候補の外のポートのほうが速いことがありうる。
  - 直線距離モデルで最適な組を候補に含めるので、その組を道路モデルで評価した値より悪くはならない。
- **直線距離モデル**（`app/routing.py`、分枝限定法）は変更しない。役割は、候補の絞り込みに使う最適な組の計算と、評価での比較（道路モデルとの差を見る）。道路モデル（`app/road_routing.py`）とは責務を分ける。

### 6.5 所要時間の算出（**確定**、2026-11-25。FOSSGIS の実環境で道路距離が返ることを確認した。engineering-notes §9.7）
- **第一案**：所要時間 = OSRM の**道路距離** ÷ ChariRoute の速度（徒歩 4.8 km/h、自転車 15 km/h）。これに貸出・返却の手続き時間（各 1 分）を加える。OSRM の `duration` は使わない。
  - 理由 1：FOSSGIS の自転車プロファイルは独自のもので、電動アシストのシェアサイクルより遅い（実測で約 8.5 km/h 相当）。
  - 理由 2：速度の前提を、直線距離モデルとそろえられる。
- **確定の条件**：Table で `annotations=distance` の道路距離を取得できることを、FOSSGIS の実環境で、少ないリクエストで確かめる。
  - researcher の調査で、routed-bike の Table に 1 回だけ `annotations=duration,distance` を付けて送り、`distances` が返っている。ただし、このアプリの User-Agent ではない。
  - 正式な確認は 6.10 の対応を決めた後に、スモークテスト（Table を徒歩と自転車で 1 回ずつ）で行う。
  - 取得できない場合は、OSRM の `duration` を使う案も含めて報告し、ユーザーにもう一度判断を求める。
- **候補の選択と画面の表示で、計算のモデルを統一する**：どちらも「距離 ÷ 速度 + 手続き時間」の同じ式（`RoadParams`）を使う。
- **Table と Route の値が違う場合**：
  - 画面の距離と所要時間は、Route の距離から同じ式で計算する（地図に描く線と数字を一致させるため）。
  - 組の選択は Table の値で行い、Route の値で選び直すことはしない（リクエスト数を増やさないため）。
  - 区間の距離の差が 10% かつ 100 m を超えたら、警告をログに出す（座標は出さず、差の割合だけ）。この差は評価の項目にもする。
  - 同じサーバー・同じプロファイルなので、差は小さいと見込んでいる（推測。スモークテストで確かめる）。
- 画面には「所要時間は、道路距離と一定の速度から求めた**推定値**です（実測ではありません）」と表示する。

### 6.6 外部 API の障害時（B 案、確定）
- OSRM が失敗したら（通信、タイムアウト、HTTP 4xx/5xx、6.4 で経路なし以外の `code`、不正な応答、全体の締め切りの超過）、**503 を返す**。
  - 直線距離モデルへの自動フォールバックはしない。ダミーの経路は出さない。
  - 画面には「道路の経路を取得できませんでした。しばらくしてから再度お試しください」と明示する。
- **タイムアウト**（実測にもとづいて変更した。engineering-notes §9.7）：
  - OSRM の Route は 4 秒、**Table は 15 秒**（自転車の Table が実測で約 9.7 秒かかったため）。1 回の検索全体の締め切りは **25 秒**で、超えたら 503（API Gateway HTTP API の統合タイムアウトの上限 30 秒より短くする）。
  - Nominatim は 4 秒。
  - Lambda は 28 秒（PHASE 6。§7.2 で 30 秒から変更）。フロントの通信タイムアウトは 35 秒。
- **自動リトライはしない**。
- 混雑（外部の 429、Lambda の同時実行数の超過）は、「混雑しています」と区別して表示する。

### 6.7 外部サービスの利用条件の守り方（ユーザーが承認済み。規約との対応表は engineering-notes §9.5）
- **リミッター**：`app/outbound.py`（仮）に、サービスごとに 1 つ、プロセス全体で共有するリミッターを置く。
  - OSRM 用：`routed-foot` と `routed-bike` で共有する。
  - Nominatim 用：別に 1 つ。
  - 仕組み：
    - `threading.Lock` を、**リクエストの送信から応答の受信まで保持する**（接続を同時に 1 つに保つ）。
    - 前回の送信から 1.1 秒経っていなければ、`time.monotonic` で計って待つ。
    - **プロセスの起動後、最初の送信の前にも 1.1 秒待つ。**
  - テストでは、時計と sleep を差し替えて確かめる。
- **リクエストのヘッダー**：
  - `User-Agent`：既定は `ChariRoute/0.1 (+https://github.com/EnKyria/chariroute-lab)`。個人のメールアドレスは入れない。
  - `Referer`：設定されているときだけ付ける（`OUTBOUND_REFERER`。本番の URL が決まったら設定する）。
- **設定**：`OSRM_FOOT_URL`、`OSRM_BIKE_URL`、`NOMINATIM_URL`（https だけを受け付ける）、`OUTBOUND_USER_AGENT`、`OUTBOUND_REFERER`。
- **ローカルでの注意**：
  - uvicorn は 1 プロセスで動かす（`--workers` を使わない）。
  - スモークテストのスクリプトと開発サーバーを、同時に FOSSGIS へ接続させない。
- **大量のアクセス、スクレイピング、負荷試験はしない。** 実 API での確認は、必要最小限のスモークテストだけにする。

### 6.8 地点検索（Nominatim）
- **流れ**：フロントから `POST /api/places/search`（本文 `{q}`）を送る。検索語が URL やアクセスログに残らないように POST にする。
- **バックエンドから Nominatim への送信**：
  - Nominatim は GET なので、検索語は Nominatim 側のログに残りうる。このことを画面に明示する。
  - パラメータ：`format=jsonv2`、`limit=5`、`countrycodes=jp`、`viewbox`（大阪市付近の矩形）+ `bounded=1`、`accept-language=ja`
- **呼び出しの条件**：
  - ユーザーが検索ボタンを押したときだけ呼ぶ。オートコンプリート、定期的な検索、網羅的な検索はしない。
  - 検索語は 2〜64 文字。
- **キャッシュ**：
  - プロセス内に置き、24 時間・最大 200 件までにする。キーは正規化した検索語。
  - 入れるのは、公開施設の検索結果（名称・表示名・座標）だけ。
  - キャッシュの内容はログに出さない。
- 検索欄に「駅名・施設名で検索してください。個人名・住所・電話番号などは入力しないでください」と書く。
- 失敗したら 503 を返し、ダミーの候補は出さない。

### 6.11 API の変更（実装で確定する）

## 7. PHASE 6：AWS デプロイの実施計画（2026-11-25、セッション 6。AWS の操作は**未承認**。コードの準備はセッション 7 で完了）

AWS の公式資料にもとづいて、aws-expert が調査した（確認日 2026-11-25）。出典の URL は engineering-notes §11 にある。
「事実」は公式資料で確認したこと、「未確認」は確認できなかったこと、「推論」は判断を表す。
**AWS の操作、リソースの作成、CLI の導入、認証情報の取得は、まだ承認されていない。** 以下の ⚠ の手順は、操作ごとにユーザーの承認を得てから実行する。
**具体的なコマンド・設定値・権限・費用は `docs/deploy.md`**（セッション 7）。この節は方針と判断を残す。

### 7.1 基本方針
- **本番（AWS）では、実 API（FOSSGIS OSRM・Nominatim）との連携を無効にしてデプロイする**（§7.3 の条件が整うまで）。
  - 無効の間、経路検索は 503（道路の経路を取得できない）を返し、ダミーの経路は出さない。
  - プリセット・GBFS・画面・帰属表示は動く。
- 最初のデプロイで確かめるのは、次の 2 つである。経路検索の成功は確かめない。
  - インフラとアプリの結合（CloudFront → S3 / API Gateway → Lambda → GBFS）
  - 障害時の表示
- インフラは必要最小限にする。IaC は MVP の後に回す。手順は AWS CLI のコマンドとして記録し、再現できるようにする。
- 一般公開しない。URL を共有しない前提で、アクセス制限を入れる（§7.6）。
- **最初の夜の優先順位**（2026-11-25 ユーザーの指示）：実 API を無効にした状態での AWS デプロイと疎通確認を優先する。ユーザー認証（§7.6）と分散リミッター（§7.3）は、その後の作業にする。
  - 認証を入れる前は、URL を共有しない。実 API は無効なので、外部サービスに送信されることはない。GBFS の取得と AWS の従量課金は発生しうるので、Budgets と緊急停止の手段を先に用意する。
- **テスト用のデータ**：使う場合は、明示的に有効にする「テストモード」として扱う。
  - テストモードは環境変数で明示的に有効にし、既定は無効とする。本番の環境では有効にしない。
  - テストモードの応答には、テスト用であることを示す項目を入れる。画面では、結果の上に「テストモード（ダミーのデータ）」と目立つように表示する。
  - 通常の検索結果として、ダミーの経路を返すことはしない（CLAUDE.md の要件）。テストモードを無効にした状態では、外部サービスが使えなければ 503 を返す。
  - 今回の PHASE 5 のブラウザ確認では、テストモードは作らず、リポジトリの外の使い捨てのスタブ API を使った。
  - **セッション 7 の判断**：テストモードは実装しない。今夜の確認（無効の状態で 503 と画面の表示）に不要で、ダミーの経路を返す経路をコードに持たないほうが要件に反しにくいため。必要になったら、上の条件で別途実装する。

### 7.2 タイムアウトの整合（事実と決定）
| 層 | 値 | 根拠 |
|---|---|---|
| HTTP API の統合タイムアウト | 30 秒（最大。**引き上げはできない**） | 事実（HTTP API のクォータ） |
| Lambda のタイムアウト | **28 秒** | 30 秒にすると API Gateway の打ち切りと重なり、アプリの 503 の本文が届かないおそれがある（推論） |
| 検索全体の締め切り（アプリ） | 25 秒（既存） | Lambda より短くし、アプリが 503 を返せるようにする |
| フロントの通信タイムアウト | 35 秒（既存） | 上のどれよりも長くする |
- 次の場合に HTTP API が返すステータス（500 / 503 / 504 / 429 のどれか）は、公式資料で確認できなかった（未確認）。
  - 統合タイムアウトになったとき
  - Lambda が throttle されたとき
- フロントは 5xx をすべて「結果を出さないエラー」として表示する。どのステータスでもダミーは出ない。
- 実際の値は §7.8 の手順 9 で確かめ、記録する。

### 7.3 実 API を本番で有効にしてよい条件（判定：**現状では満たさない**）
**今の設計（プロセス内のリミッター + 予約済み同時実行数 1）だけでは、「アプリ全体で 1 秒 1 回以下・同時接続 1」を保証できない。** 理由は次の 3 つ。
1. 古い実行環境と新しい実行環境の処理が、タイムアウトや異常終了の前後で時間的に重ならない、という公式の記述がない。
   - 実行環境は、タイムアウトやクラッシュのときにリセットされる。数時間ごとにも入れ替わる。
   - 凍結中に終わっていなかった処理は、環境が再利用されたときに再開しうる。
2. 予約済み同時実行数 1 を設定できない可能性がある。
   - 新規アカウントは、アカウントの同時実行数の上限が引き下げられている（事実）。
   - 予約できるのは「未予約分 − 100」まで。上限が小さいと、1 も、緊急停止用の 0 も設定できない可能性がある（具体的な値は未確認）。
3. AWS の外のプロセス（ローカルの uvicorn など）との同時利用は、AWS 側では防げない。

**有効にする条件**（すべてを満たし、ユーザーが承認したときだけ）：
- (a) 実 API の利用を環境変数のフラグで切り替えられること。**既定は無効**とする。コードの変更が必要（§7.8 の手順 1）。
- (b) **分散リミッター**を使うこと。行はサービスごとに 1 つ（`osrm`、`nominatim`）。料金はオンデマンドで、1,000 検索（書き込み 5,000 回）で約 $0.003（us-east-1 の単価で試算。失敗した条件付き書き込みも課金されるかは未確認）。設計で考慮すること（2026-11-25 ユーザーの補足）：
  - **通信中の排他制御（同時接続 1）**：間隔だけでなく、送信から応答の受信までを排他にする。
    - 取得：条件「保持者がいない、またはリースが期限切れ」かつ「`next_allowed_at <= now`」で、`holder`（実行ごとのランダムな ID）・`lease_until = now + そのリクエストのタイムアウト + 余裕`・`sent_at = now` を書く。
    - 解放：応答を受け取ったら（失敗でも）、条件「`holder` が自分」で、`holder` を消し、`next_allowed_at = sent_at + 1.1 秒 + 余裕` を書く。
    - 取得できなければ送らない。待つのは検索の締め切りの範囲内だけにし、超えたら 503（`*_busy`）にする。
  - **時刻のずれ**：条件の判定には、書き込むクライアントの時計を使う（DynamoDB の条件式でサーバーの時刻は使えない、と理解している。未確認）。
    - Lambda どうしの時計のずれは小さいと見込む（推論。根拠となる公式の記述は PHASE 6 で確認する）。
    - ずれを吸収するために、余裕（例：0.5 秒）を足す。
    - ローカルの PC は時計がずれうるので、ローカルからはリースに参加させない。本番で実 API を有効にしている間は、ローカルで実 API を使わない運用にする（ローカルの実 API は、既定で無効のフラグを明示的に有効にしたときだけ使う）。
  - **異常終了**：解放の前に実行環境がタイムアウト・クラッシュで止まると、リースが残る。
    - `lease_until` を過ぎるまで、ほかの実行は送れない（安全側）。`lease_until` は、リクエストのタイムアウト（Table 15 秒）+ 余裕にする。止まった環境のソケットが、その後に送信を続けることはないと見込む（推論）。
    - 残ったリースの間、検索は 503（混雑）になる。自動リトライはしない。
  - **プロセス内のリミッターは残す**：DynamoDB の前段で、同じプロセスの中の直列化に使う。
  - DynamoDB 自体の障害・スロットリングで書き込めないときは、送らずに 503 にする（フォールバックで送らない）。
  - テストは、偽の DynamoDB クライアントと差し替えた時計で書く（取得の競合、解放の条件、期限切れ、時計のずれ、異常終了後の待ち）。
  - IAM は `dynamodb:UpdateItem`（と必要なら `GetItem`）を、そのテーブルの ARN 1 つに絞る。
- (c) 予約済み同時実行数を 1 に設定し、`get-function-concurrency` で確認できること。これは保証の根拠ではなく、多重化を減らすための補助である。
- (d) 緊急停止（§7.9）を事前に 1 回試し、復旧まで確認したこと。
- (e) `OUTBOUND_REFERER` に本番の URL を設定したこと（FOSSGIS の規約の Referer）。

満たせない間は、本番の経路検索は 503 のままにする。本番で経路を出す別の方法として、自前の OSRM（EC2 など。費用がかかる）がある。これは MVP の後に検討する。

### 7.4 Lambda のデプロイパッケージ
**実装済み（セッション 7、`scripts/build_lambda.py`）。実際のビルドで分かったこと（事実）**：
- `--platform manylinux_2_28_x86_64` だけでは、pip 26.3 は古いタグの wheel を候補にせず、`pydantic-core==2.50.4` が見つからなかった（PyPI にあるのは `manylinux_2_17_x86_64.manylinux2014_x86_64`）。→ `manylinux_2_28` / `manylinux_2_17` / `manylinux2014` の 3 つを指定した。
- 入った wheel：ネイティブ拡張は `pydantic_core` の `.so` 1 つだけ（タグ `cp312-cp312-manylinux_2_17_x86_64`、x86_64 の ELF、要求する glibc は最大 2.14）。ほかは全て `py3-none-any`。
- 間接依存（starlette 1.10.0 など）は requirements.txt で固定されていなかった → venv の `pip freeze` を制約にして、テストと同じ版を入れる。
- pip が Windows で作る `bin/*.exe` が入る → 除き、RECORD からも消す。同じ入力から同じ zip（バイト単位で一致）になる。
- zip 約 3.3 MB・展開後 約 10 MB（上限 50 MB / 250 MB）。Lambda 上での import の確認は `docs/deploy.md` §4.5。
- 以下は当初の計画（参考）。

- ランタイムは python3.12（Amazon Linux 2023）、アーキテクチャは x86_64。
  - python3.12 のサポート終了（deprecation）は 2028-10-31（事実）。
  - arm64 は利点が小さいので見送る。
- 依存のインストールのタグは **`manylinux_2_28_x86_64`** を使う。`manylinux2014` は Python 3.11 以前（AL2）向け（事実）。
  ```bash
  backend/.venv/Scripts/python.exe -m pip install -r backend/requirements.txt \
    --platform manylinux_2_28_x86_64 --implementation cp --python-version 3.12 \
    --only-binary=:all: --target build/lambda
  ```
  - Windows でインストールした site-packages は、そのまま使わない。pydantic_core のネイティブ拡張が Windows 用になるため。
  - `--only-binary=:all:` で失敗したら、対応する wheel がないことが分かる。その時点で対処を判断する。
  - **補足（2026-11-25 ユーザーの指摘）**：AWS の資料が Python 3.12 に `manylinux_2_28` を案内していることは、`manylinux2014` の wheel が Python 3.12 のランタイムで動かない、という意味ではない。manylinux のタグは「その glibc 以上の環境で動く」ことを表すので、`manylinux2014`（glibc 2.17）の wheel も、より新しい glibc の環境で動きうる（推論。Amazon Linux 2023 の glibc の版は PHASE 6 で公式資料を確認する）。
  - したがって、タグの名前ではなく、**実際に入った wheel と依存ライブラリの互換性**を確かめる。
    - インストール後に、各パッケージの `*.dist-info/WHEEL` の `Tag` を一覧にして記録する（特に `pydantic_core`。cp312・x86_64・manylinux であること）。
    - pip が、指定したタグより古い manylinux のタグの wheel も受け入れるかは、実際のインストール結果で確かめる。
    - ネイティブ拡張のある依存が `pydantic_core` だけであることを確かめる（`.so` の一覧）。
    - 最終的な確認は、Lambda 上での import（`/health` と `/api/presets` の 200）と、Mangum 経由の検索（実 API は無効なので 503 が返ること）で行う。
- `backend/main.py` と `backend/app/` をコピーし、`__pycache__`・`tests/`・`tools/` を除いて zip にする。
  - 上限は、zip が 50 MB（直接アップロード）、解凍後が 250 MB（事実）。
- 手順はスクリプト（`scripts/build_lambda.py`、標準ライブラリだけ）にして、リポジトリに入れる。
  - 成果物（`build/`）は Git 管理の対象外にする。
  - 旧成果物の `package/` と `deployment.zip` は使わない（削除もしない）。
- **ビルドの確認**（AWS に接続しない）：
  - zip のサイズ
  - `pydantic_core` の `.so` が `manylinux` 用であること
  - `main.handler` を import できること。手元に Linux の Python がないので、この確認は Lambda 上で行う。

### 7.5 API Gateway HTTP API と Lambda
- 構成：HTTP API、Lambda プロキシ統合、payload format 2.0、ステージは `$default`（自動デプロイ）。
- ルートは `$default` にし、すべてのパスを Lambda に渡す。ルーティングは FastAPI が行う。
- ルートのスロットリングは、たとえばレート 1・バースト 2 にする。
  - スロットリングは **best-effort**（事実）。外部 API の規約を守る根拠にはせず、過剰な呼び出しを抑える補助として使う。
- CORS は設定しない。CloudFront の同一オリジンで `/api/*` を振り分けるため。

### 7.6 認証とアクセス制限
**オリジンへのアクセス制限と、ユーザー本人の認証は、別の仕組みとして扱う**（2026-11-25 ユーザーの補足）。
- (1) オリジンへのアクセス制限：API Gateway を、CloudFront を経由しない直接の呼び出しから守る。「誰が使っているか」は判定しない。
- (2) ユーザーの認証：画面と API を使えるのが、ユーザー本人だけであることを確かめる。
- 共有シークレットのヘッダーは (1) であり、(2) の代わりにはならない（CloudFront の URL を知っていれば、誰でも CloudFront 経由で呼べる）。

HTTP API で使えるのは、Lambda オーソライザー・JWT オーソライザー・IAM の 3 つ（事実）。API キーや使用量プランは REST API の機能である。

**(1) オリジンへのアクセス制限 — 採用案（追加費用なし）**：共有シークレットのカスタムヘッダーで、CloudFront 経由のリクエストだけを通す。
  - CloudFront が、オリジン（API Gateway）へのリクエストにヘッダーを付ける。
  - FastAPI のミドルウェアでヘッダーを検証し、なければ 403 にする。外部 API や GBFS を呼ぶ前に止められる。
  - シークレットは、Lambda の環境変数と CloudFront のオリジン設定にだけ置く。`VITE_` の環境変数にも、リポジトリにも入れない。
  - 弱点：
    - シークレットが漏れると破られる。
    - API Gateway の呼び出しそのもの（とその課金）は止められない。
    - 個人利用で無料枠の範囲なら、許容できる。
- 既定の execute-api のエンドポイントを無効にする機能は、カスタムドメインが前提（事実）。独自ドメインと証明書が要るので、MVP では使わない。

**(2) ユーザーの認証 — 候補**（個人利用・固定費を抑える。料金と制約は、PHASE 6 で公式資料を確認してから決める。下の表の料金は**未確認**）：
| 方式 | 守れる範囲 | 固定費 | 長所 | 短所 |
|---|---|---|---|---|
| **A. CloudFront Functions の Basic 認証**（viewer request で `Authorization` を検証） | 画面と API の両方（全てのビヘイビアに付ける） | なし（リクエスト単位の従量。未確認） | 構成が最小。アプリのコードを変えない。CloudFront の入口で止めるので、オリジンに届かない | 資格情報は CloudFront Functions の KeyValueStore か関数のコードに置く（リポジトリには入れない）。MFA なし。ログアウトはブラウザ任せ。資格情報の変更は関数の更新 |
| B. Amazon Cognito のユーザープール + HTTP API の JWT オーソライザー | API（画面の静的ファイルは別に守る必要がある） | 少ない MAU なら無料枠の見込み（未確認） | MFA を使える。標準的な OAuth 2.0 / OIDC | フロントにログインの処理（Hosted UI とトークンの扱い）が要る。設定が多く、今夜のスコープを超える |
| C. AWS WAF の IP 制限 | 画面と API | 月 $6 程度〜（事実） | パスワード不要 | 固定費がかかる。モバイル回線では IP が変わる |
| D. Lambda@Edge で認証 | 画面と API | なし（従量） | 柔軟 | us-east-1 での管理、ログが各リージョンに分散し、複雑 |
- **推奨（案）**：まず **A（Basic 認証）**。固定費がなく、画面と API の両方を CloudFront の入口で守れる。HTTPS（CloudFront の既定の証明書）の上で使う。
  - (1) の共有シークレットと組み合わせる（A は利用者を、(1) は CloudFront を通らない呼び出しを止める）。
  - MFA などが必要になったら B に移る。
  - 資格情報の作成と保管はユーザーが行う（Claude は値を見ない、ログやリポジトリに残さない）。
- **今夜の扱い**：実 API を無効にしたデプロイと疎通確認を優先する（§7.1）。A は、その後に追加する。追加するまでは URL を共有しない。
- **セッション 7 の変更（ユーザーの指示「CloudFront Functions の Basic 認証を第一候補、HTTPS 必須、一般公開前に認証とアクセス制限を有効化」）**：
  - A を `infra/cloudfront/basic-auth.js` として実装した（テスト付き）。KeyValueStore には資格情報の平文ではなく、`Authorization` ヘッダーの値の SHA-256 だけを置く。KeyValueStore の不備は 503（安全側）。
  - **ディストリビューションは最初から A を付けて作る**（`docs/deploy.md` §5.2）。認証なしで URL が開いている時間を作らないため。追加の費用はほぼない（§7.11、deploy.md §9）。
  - HTTPS は、ビヘイビアの Viewer protocol policy を `https-only` にして強制する（関数のイベントには閲覧者のプロトコルの項目がない。事実）。
  - (1) の共有シークレットは、Lambda 上では**必須**にした（未設定・短すぎるときは全て 403）。CloudFront は、閲覧者が同じ名前のヘッダーを送っても値を上書きする（事実）。`Authorization` は既定でオリジンに転送されず（事実）、関数でも消す。

### 7.7 S3 + CloudFront
- **S3**（事実）：
  - バケットは非公開にし、Block Public Access はすべて有効にする。
  - OAC を使い、署名は always にする。
  - バケットポリシーで `cloudfront.amazonaws.com` に `s3:GetObject` を許可し、`AWS:SourceArn` にディストリビューションの ARN を指定する。
- **ビヘイビア**：
  - 既定（`*`）→ S3。
    - default root object は `index.html`。
    - キャッシュはマネージドポリシーの `CachingOptimized`。
  - `/api/*` → HTTP API。
    - キャッシュは `CachingDisabled`、オリジンリクエストポリシーは `AllViewerExceptHostHeader`（事実）。
    - 許可するメソッドは GET・HEAD・OPTIONS・PUT・POST・PATCH・DELETE（検索と地点検索で POST を使うため）。
  - SPA のルーティングはないので、403/404 を `index.html` に返すエラーレスポンスは設定しない（存在しないパスは 404 のまま）。
- **レスポンスヘッダー**：`Referrer-Policy` を `no-referrer` にしない。OSM のタイルに Referer を送るため（engineering-notes §8）。
  - マネージドの `SecurityHeadersPolicy`（`strict-origin-when-cross-origin`）なら、オリジンが送られるので使ってよい（推論）。
- CloudFront の標準ログは有効にしない。
- **注意**：CloudFront のフラットレート料金プラン（Free プランを含む）に加入すると、請求サイクルの終わりまでディストリビューションを削除できない（事実）。従量課金のままにするか、加入するなら削除の時期に注意する。

### 7.9 緊急停止
| 手段 | 効果と即時性 | 復旧 |
|---|---|---|
| Lambda の予約済み同時実行数を 0 にする | 関数の実行を止める（事実）。即時性は公式に記載がない | `put-function-concurrency` で 1 に戻す（または `delete-function-concurrency`） |
| 環境変数で実 API を無効にする | 外部への送信だけを止める。新しい実行環境から反映される（推論） | フラグを戻す |
| CloudFront のディストリビューションを無効にする | 画面と API の入口を止める。反映に数分かかる | 有効にする |
| HTTP API のスロットリング | best-effort。0 を使えるかは未確認なので、停止の手段にしない | — |
- 予約済み同時実行数を設定できないアカウントでは、環境変数のフラグと CloudFront の無効化を使う。
