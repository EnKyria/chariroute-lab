## 2. 経路計算（直線距離モデル、PHASE 3。PHASE 4.5 以降は候補の絞り込みと比較評価に使う。道路モデルは §6）

```
合計所要時間 = 徒歩(出発地 → 貸出ポート A) + 自転車(A → 返却ポート B) + 徒歩(B → 目的地)
```
- 距離はハバーサイン式で求めた直線距離 × 迂回係数（初期値 1.3）。
- 速度の初期値は徒歩 4.8 km/h、自転車 15 km/h。貸出・返却の手続き時間として各 1 分を加える。
- 候補の選び方：
  - A は「貸出可能な」全てのポート、B は「返却可能な」全てのポート。A = B の組は除く。
  - 全ての (A, B) の中で合計が最小の組を採用する。**この所要時間モデルでの最適解を保証する**（2026-11-25 変更）。
  - 計算は分枝限定法（合計の下限で、最適解になりえない組を打ち切る）。結果は全探索と同じで、実データでは 1 回 約 3ms（素朴な総当たりは約 0.7 秒）。根拠と計測は `docs/engineering-notes.md` §2・§7。
  - 当初の「近い順に K=10 件ずつ」の方式は、最適解を保証しないため廃止した。
- 徒歩のみの所要時間も計算して並べて返す。自転車のほうが遅い場合もそのまま返し、UI で判断できるようにする。→ **PHASE 4.5 で廃止**（徒歩のみ・比較・おすすめは扱わない。§6.3）
- パラメータは定数にまとめ、テストで値を固定する（評価駆動：代表的な地点ペアの結果を比較できるようにする）。

## 3. API（PHASE 3 で実装済み。PHASE 4.5 で §6.11 のとおり変更する）
- `GET /health`
- `GET /api/presets`：プリセット地点の一覧（id, name, lat, lon）。8 か所。`backend/app/presets.py` だけで定義する。
- `POST /api/routes/search`：`{origin_id, destination_id}` を受け取り、`origin`、`destination`、`recommended`（`bike_share` / `walk`）、`bike_share`（ポート A/B、各区間の距離と所要時間、合計。候補がなければ `null`）、`walk`、`data`（`last_updated`（JST）、提供者、ライセンス、クレジット表記）を返す。
  - 旧 `{origin, destination}` 文字列 API からの仕様変更。特性テストは置き換えた。
  - 判定の順序は 422（形式）→ 400（不明な地点・同じ地点）→ 503（GBFS の取得失敗）。
  - 503 にする条件：通信エラー、タイムアウト、HTTP エラー、不正な JSON、必須構造の欠落、大阪エリアのポートが 0 件、データが 900 秒より古い、`last_updated` が 300 秒より未来。
  - キャッシュは経過時間が ttl（フィードの値、上限 300 秒）未満で、かつデータが古すぎない間だけ使う。期限切れのキャッシュは失敗時にも返さない。
  - 個々のポートのレコードが不正なら、そのポートだけを捨てる。
  - `bike_share` は、利用可能な全ての貸出・返却ポートの組の中で合計所要時間が最小の組（このモデルでの最適解）。所要時間は直線距離 × 迂回係数による概算で、実際の道路の経路ではない。
  - `data.attribution` はクレジット表記（「出典：株式会社ドコモ・バイクシェア / 公共交通オープンデータ協議会（CC BY 4.0）のポート情報を加工して作成」）。`data.dataset_url` はデータセットのページ。

## 6. PHASE 4.5：地点指定の拡張と道路に沿った経路（**確定**、2026-11-25）

ユーザー受入テスト（PHASE 4）の結果を受けて、ユーザーが最終決定した仕様。これまでの計画（ORS 案、OSRM の初版）と矛盾する場合は、この節を優先する。
**状態：実装済み（2026-11-25、セッション 5、ブランチ `feature/phase45-implementation`）。** 6.10 は解決した。実装で決めた点と実 API の確認結果は engineering-notes §9.7。

### 6.1 サービスの目的
- 大阪市内でドコモ・バイクシェアを使う前提で、効率的な**貸出ポートと返却ポートの組み合わせ**を探す。
- Google マップなどの既存のサービスとの差別化を重視し、シェアサイクル固有の課題に集中する。課題とは、空き台数と返却枠、ポートの選び方、乗り換えの徒歩のこと。

### 6.2 技術選定（確定）
| 役割 | 採用 |
|---|---|
| ポート情報 | ODPT の GBFS（既存） |
| 道路の経路 | FOSSGIS OSRM（`routed-foot` / `routed-bike`） |
| 地点検索 | Nominatim |
| 現在地 | ブラウザの Geolocation API |
| 地図 | Leaflet + OpenStreetMap |
| バックエンド / フロント | Python・FastAPI / React・TypeScript |
| 本番 | AWS（PHASE 6） |

- 新規の API キー、有料の契約、クレジットカードの登録が要らない構成を維持する。**openrouteservice は採用しない。**

### 6.3 機能
- **地点の指定**：
  - 指定の方法：現在地（GPS）、地点検索（駅名・公開施設名）、プリセット、地図のタップ
  - 出発地と目的地は、どちらも自由に設定でき、入れ替えられる。
  - GPS は、次の状態をそれぞれ画面に表示する：権限の拒否、タイムアウト、非対応、取得の失敗、HTTPS でない。
- **経路**：3 区間（徒歩：出発地 → 貸出、自転車：貸出 → 返却、徒歩：返却 → 目的地）。
  - 区間ごとに、道路に沿った経路（地図に実線で描く）、道路距離、推定所要時間を表示する。
  - 合計の推定所要時間も表示する。
  - 貸出・返却ポートの名称、利用可能な台数と返却できる枠の数、GBFS の取得時刻も表示する。
- **廃止する機能**（Google マップで確認できるため）：徒歩のみの経路の計算と表示、徒歩との所要時間の比較、おすすめの移動手段の判定、時間の短縮効果の表示。
  - API の `recommended` と `walk` を削除する。あわせて、TypeScript の型、UI（比較・おすすめの表示）、テスト、ドキュメントを整理する。
  - テストの削除・変更の理由は、コミットメッセージと PR に書く。
- **利用できる経路がない場合**：利用できるポートの組や、道路でつながる組がないときは、「利用できるシェアサイクルの経路が見つかりませんでした」と明示する。徒歩への自動の切り替えはしない。

### 6.4 経路探索のアルゴリズム
1. GBFS から、利用可能な貸出ポート（`is_renting` かつ空き自転車 > 0）と返却ポート（`is_returning` かつ空きドック > 0）を取り出す（既存の処理）。
2. **候補を絞り込む**（直線距離）：
   - 貸出候補：出発地から近い順に 10 件 + 直線距離モデル（分枝限定法）で最適な組の貸出ポート
   - 返却候補：目的地から近い順に 10 件 + 同じく返却ポート
   - それぞれ重複を除く。**最大の候補数は、貸出・返却とも 11 件**。
   - 同じポートが両方の候補に入ることはありうる。その場合でも、貸出と返却が同じポートの組は評価しない。
3. **Table を 2 回呼ぶ**（`annotations=distance`。所要時間は使わない。6.5）：
   - 徒歩（routed-foot）：
     - 地点は [出発地, 貸出候補 ≤11, 返却候補 ≤11, 目的地] の **最大 24 点**。
     - `sources = [出発地, 返却候補…]`、`destinations = [貸出候補…, 目的地]` とし、**最大 12×12 = 144 要素**を得る。
     - 使うのは、出発地 → 貸出候補（≤11）と、返却候補 → 目的地（≤11）の 22 要素。
     - 1 回で済ませるため、残りの要素は捨てる。
   - 自転車（routed-bike）：地点は [貸出候補 ≤11, 返却候補 ≤11] の **最大 22 点**。貸出候補 × 返却候補で **最大 11×11 = 121 要素**。
   - どちらも、OSRM の既定の上限（100 地点）より十分小さい。
4. **全ての組を評価する**：候補の全ての組（最大 121 組。貸出と返却が同じポートの組は除く）について、合計の推定所要時間を計算し、最小の組を選ぶ。
   - 合計 = 徒歩の距離 ÷ 4.8 km/h + 貸出の手続き 1 分 + 自転車の距離 ÷ 15 km/h + 返却の手続き 1 分 + 徒歩の距離 ÷ 4.8 km/h
   - 同じ値の組は、既存と同じ ID の順で決める。
5. **Route を 3 回呼ぶ**：選ばれた組の 3 区間について、`overview=full&geometries=geojson` で経路の形状と距離を取得する。
- **1 回の検索のリクエスト数**：Table 2 回 + Route 3 回 = **5 回**（GBFS を除く）。
- **null と通行できない組の扱い**：
  - Table の距離が `null`（到達できない）なら、その区間を含む組を除外する。
  - 貸出候補へ徒歩で到達できない、または目的地へ徒歩で到達できない場合は、そのポートを候補から除く。
  - 残った組が 0 件なら、「利用できるシェアサイクルの経路が見つかりませんでした」（`bike_share: null`、HTTP 200）にする。
  - OSRM の `code` が `NoTable` / `NoRoute` / `NoSegment` の場合も、経路なしとして扱う。それ以外のエラー（`InvalidQuery`、`TooBig`、HTTP 5xx、タイムアウト、不正な応答）は 503 にする。
- **地点のスナップ**：出発地か目的地が道路から大きく離れている場合（Table の `sources` / `destinations[].distance` が 300 m を超える）は、400「近くに道路が見つかりません」にする。値は実装で調整する。
- **最適性の制約（画面とドキュメントに明示する）**：
  - 結果は「直線距離で絞り込んだ候補（最大 11×11 組）の中で、推定所要時間が最小」の組である。**全てのポートの組の中での最適解は保証しない**。
  - 川や橋で遠回りが必要な場合は、候補の外のポートのほうが速いことがありうる。
  - 直線距離モデルで最適な組を候補に含めるので、その組を道路モデルで評価した値より悪くはならない。
- **直線距離モデル**（`app/routing.py`、分枝限定法）は変更しない。役割は、候補の絞り込みに使う最適な組の計算と、評価での比較（道路モデルとの差を見る）。道路モデル（`app/road_routing.py`）とは責務を分ける。

### 6.5 所要時間の算出（**確定**、2026-11-25。FOSSGIS の実環境で道路距離が返ることを確認した。engineering-notes §9.7）
- **第一案**：所要時間 = OSRM の**道路距離** ÷ ChariRoute の速度（徒歩 4.8 km/h、自転車 15 km/h）。これに貸出・返却の手続き時間（各 1 分）を加える。OSRM の `duration` は使わない。
  - 理由 1：FOSSGIS の自転車プロファイルは独自のもので、電動アシストのシェアサイクルより遅い（実測で約 8.5 km/h 相当）。
  - 理由 2：速度の前提を、直線距離モデルとそろえられる。
- **確定の条件**：Table で `annotations=distance` の道路距離を取得できることを、FOSSGIS の実環境で、少ないリクエストで確かめる。
  - researcher の調査で、routed-bike の Table に 1 回だけ `annotations=duration,distance` を付けて送り、`distances` が返っている。ただし、このアプリの User-Agent ではない。
  - 正式な確認は 6.10 の対応を決めた後に、スモークテスト（Table を徒歩と自転車で 1 回ずつ）で行う。
  - 取得できない場合は、OSRM の `duration` を使う案も含めて報告し、ユーザーにもう一度判断を求める。
- **候補の選択と画面の表示で、計算のモデルを統一する**：どちらも「距離 ÷ 速度 + 手続き時間」の同じ式（`RoadParams`）を使う。
- **Table と Route の値が違う場合**：
  - 画面の距離と所要時間は、Route の距離から同じ式で計算する（地図に描く線と数字を一致させるため）。
  - 組の選択は Table の値で行い、Route の値で選び直すことはしない（リクエスト数を増やさないため）。
  - 区間の距離の差が 10% かつ 100 m を超えたら、警告をログに出す（座標は出さず、差の割合だけ）。この差は評価の項目にもする。
  - 同じサーバー・同じプロファイルなので、差は小さいと見込んでいる（推測。スモークテストで確かめる）。
- 画面には「所要時間は、道路距離と一定の速度から求めた**推定値**です（実測ではありません）」と表示する。

### 6.6 外部 API の障害時（B 案、確定）
- OSRM が失敗したら（通信、タイムアウト、HTTP 4xx/5xx、6.4 で経路なし以外の `code`、不正な応答、全体の締め切りの超過）、**503 を返す**。
  - 直線距離モデルへの自動フォールバックはしない。ダミーの経路は出さない。
  - 画面には「道路の経路を取得できませんでした。しばらくしてから再度お試しください」と明示する。
- **タイムアウト**（実測にもとづいて変更した。engineering-notes §9.7）：
  - OSRM の Route は 4 秒、**Table は 15 秒**（自転車の Table が実測で約 9.7 秒かかったため）。1 回の検索全体の締め切りは **25 秒**で、超えたら 503（API Gateway HTTP API の統合タイムアウトの上限 30 秒より短くする）。
  - Nominatim は 4 秒。
  - Lambda は 30 秒（PHASE 6）。フロントの通信タイムアウトは 35 秒。
- **自動リトライはしない**。
- 混雑（外部の 429、Lambda の同時実行数の超過）は、「混雑しています」と区別して表示する。

### 6.7 外部サービスの利用条件の守り方（ユーザーが承認済み。規約との対応表は engineering-notes §9.5）
- **リミッター**：`app/outbound.py`（仮）に、サービスごとに 1 つ、プロセス全体で共有するリミッターを置く。
  - OSRM 用：`routed-foot` と `routed-bike` で共有する。
  - Nominatim 用：別に 1 つ。
  - 仕組み：
    - `threading.Lock` を、**リクエストの送信から応答の受信まで保持する**（接続を同時に 1 つに保つ）。
    - 前回の送信から 1.1 秒経っていなければ、`time.monotonic` で計って待つ。
    - **プロセスの起動後、最初の送信の前にも 1.1 秒待つ。**
  - テストでは、時計と sleep を差し替えて確かめる。
- **リクエストのヘッダー**：
  - `User-Agent`：既定は `ChariRoute/0.1 (+https://github.com/EnKyria/chariroute-lab)`。個人のメールアドレスは入れない。
  - `Referer`：設定されているときだけ付ける（`OUTBOUND_REFERER`。本番の URL が決まったら設定する）。
- **設定**：`OSRM_FOOT_URL`、`OSRM_BIKE_URL`、`NOMINATIM_URL`（https だけを受け付ける）、`OUTBOUND_USER_AGENT`、`OUTBOUND_REFERER`。
- **ローカルでの注意**：
  - uvicorn は 1 プロセスで動かす（`--workers` を使わない）。
  - スモークテストのスクリプトと開発サーバーを、同時に FOSSGIS へ接続させない。
- **大量のアクセス、スクレイピング、負荷試験はしない。** 実 API での確認は、必要最小限のスモークテストだけにする。

### 6.8 地点検索（Nominatim）
- **流れ**：フロントから `POST /api/places/search`（本文 `{q}`）を送る。検索語が URL やアクセスログに残らないように POST にする。
- **バックエンドから Nominatim への送信**：
  - Nominatim は GET なので、検索語は Nominatim 側のログに残りうる。このことを画面に明示する。
  - パラメータ：`format=jsonv2`、`limit=5`、`countrycodes=jp`、`viewbox`（大阪市付近の矩形）+ `bounded=1`、`accept-language=ja`
- **呼び出しの条件**：
  - ユーザーが検索ボタンを押したときだけ呼ぶ。オートコンプリート、定期的な検索、網羅的な検索はしない。
  - 検索語は 2〜64 文字。
- **キャッシュ**：
  - プロセス内に置き、24 時間・最大 200 件までにする。キーは正規化した検索語。
  - 入れるのは、公開施設の検索結果（名称・表示名・座標）だけ。
  - キャッシュの内容はログに出さない。
- 検索欄に「駅名・施設名で検索してください。個人名・住所・電話番号などは入力しないでください」と書く。
- 失敗したら 503 を返し、ダミーの候補は出さない。

### 6.9 プライバシーと表示
- **保存しない**：GPS の座標、検索語、個人情報を、自アプリのログ（エラーログを含む）、キャッシュ（地点検索の結果を除く）、永続ストレージ（localStorage を含む）に保存しない。ログに出すのは、入力の種類（preset / gps / place / map）、処理時間、結果の種類だけ。
- **事前の明示**（検索ボタンの近く）：「経路計算のため、出発地・目的地の座標を外部サービス（FOSSGIS の OSRM、ドイツ）に送信します。送信した内容は、FOSSGIS のサーバーログに記録されます」
- **帰属表示**：
  - 地図上：「© OpenStreetMap contributors」（既存）
  - 結果欄：
    - 「経路：OSRM / FOSSGIS（routing.openstreetmap.de）」
    - 「地点検索：Nominatim / OpenStreetMap」
    - 「地図の誤りを報告」（https://www.openstreetmap.org/fixthemap）
    - GBFS の出典（既存）

### 6.11 API の変更（実装で確定する）
- `POST /api/routes/search`：
  - リクエストは `{origin: Location, destination: Location}`。`Location` は `{preset_id}` か `{lat, lon, source: "gps"|"place"|"map"}`。
    - 座標は `OSAKA_BBOX` の外なら 400 にする。
    - 旧形式の `origin_id` / `destination_id` は廃止する。
  - レスポンスから `recommended` と `walk` を削除する。
  - `bike_share` には、3 区間（`legs`）を入れる。各区間は `mode`、`distance_m`（道路距離）、`minutes`、`geometry`（`[[lat, lon], ...]`）。あわせて手続き時間、`total_minutes`、ポート（名称・台数・枠数）を持つ。
  - 経路がなければ `bike_share: null`。
  - `data` に、経路データの出典（OSRM / FOSSGIS / OSM）を追加する。
- `POST /api/places/search`：`{q}` → `{places: [{name, label, lat, lon}]}`。失敗したら 503。

### 6.12 テストと評価
- 既存の品質ゲートと CI を維持する。自動テストでは外部のネットワークに接続せず、フィクスチャとスタブを使う。
- 仕様の変更で不要になるテスト（徒歩との比較、おすすめの判定、時間の短縮効果）は、理由を明記して変更または削除する。直線距離モデルのテスト（427 件の大部分）は残す。
- **重点的に評価する項目**：
  - 川や橋を考慮した道路の経路（フィクスチャで、直線距離では近いが道路では遠いポートを選ばないこと）
  - 貸出・返却ポートの選択と、台数・枠数による除外
  - 通行できない組（`null`）
  - 利用できるポートがない場合
  - Table と Route の整合性
  - API の障害とタイムアウト（503）
  - レートリミッターの動作（間隔 1.1 秒、直列、初回の待機、リトライしないこと）
  - GPS の取得の失敗
  - 地点検索の失敗
  - スマートフォンでの操作性
- evaluator（実装の前）と reviewer（実装の後）を使う。
